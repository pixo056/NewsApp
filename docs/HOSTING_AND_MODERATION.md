Исследование на 22.10.2026. Сервера не создавались, оплата/домен не оформлялись, HTTPS и нейросеть не подключались. Ни один материал приложения не отправлялся внешней нейросети.

## Что нужно приложению

Для демонстрации предлагаю один Linux VPS: 2 vCPU, 4 ГБ RAM, 40–50 ГБ постоянного SSD; Java 25, PostgreSQL, FFmpeg и веб-сервер с HTTPS. Это оценка для нескольких тестировщиков и одной обработки видео одновременно, а не результат облачного нагрузочного теста. 2 ГБ можно пробовать с ограничением памяти Java и уменьшенными видео, но запас для PostgreSQL и FFmpeg мал. GPU для приложения не нужен.

Фото/видео следует хранить на постоянном диске или в отдельном объектном хранилище; PostgreSQL хранит аккаунты, тексты, метаданные и решения. Обычный хостинг только для статических сайтов Java backend не запустит. Windows-лаунчеры проекта не переносятся на Linux как есть: потребуется подготовить production-запуск, пути FFmpeg, сборку фронтенда, переменные окружения, автозапуск и резервное копирование. Сейчас этого развёртывания не выполняли.

## Как это даст HTTPS и PWA

После выбора сервера: домен/поддомен → HTTPS reverse proxy → собранный React + Spring API по одному origin. Для общего доверенного HTTPS возможен Caddy с автоматическим сертификатом или Nginx с Let's Encrypt; стоимость домена отдельно. Нужно проверить proxy-лимит загрузки и таймауты, Secure cookies, хранение сессий, закрытую БД и недоступность тестовой почты извне. Нельзя просто выставить Vite dev-server в интернет.

На телефоне PWA требует доверенного HTTPS (исключение localhost относится к самому устройству, а не Wi-Fi IP ноутбука). После размещения проверяются manifest, service worker и установка в Samsung Internet. Сервер после установки всё равно должен работать; PWA не переносит PostgreSQL и видео на телефон. [Требования установки PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable), [автоматический HTTPS Caddy](https://caddyserver.com/docs/automatic-https).

## Пункт 10: сначала автоматизация без нейросети

Уже работают ограничения длины/форматов/длительности, квоты, права, подтверждение почты и ручные очереди. Я предлагаю дополнить их проверкой точных повторов заголовка/текста/вложений одного автора, всплесков повторных заявок и количества ссылок. Подозрительные случаи получать понятные метки: «возможный повтор», «много ссылок», «проверьте контактные данные». Наличие контакта, спорного слова или цитаты само по себе не доказывает нарушение, поэтому такие метки не отклоняют новость автоматически.

Модератор видит причины и выделенные фрагменты, а не абстрактный «рейтинг плохой новости». Первая версия не принимает решений о содержании за человека и не обходит два этапа публикации. Автоматически отклонять можно только однозначно невыполненные технические требования, как уже делает валидация. Проверка источника здесь означает наличие/формат ссылки, не истинность текста; сервер не должен бесконтрольно скачивать пользовательские URL.

Это мой рекомендуемый ближайший шаг: бесплатно, понятно на защите, без установки тяжёлого ПО. Здесь он только описан, новых автоматических проверок не добавлено.

## Если нужна именно нейросеть

Предлагаю локальную **Qwen3-4B-Instruct-2507** через **Ollama**, фиксированный тег `qwen3:4b-instruct-2507-q4_K_M`. Модель текстовая, веса этой квантизации около **2,5 ГБ**, лицензия Apache 2.0. Ollama запускает её отдельным процессом и предоставляет локальный HTTP API. [Карточка Qwen](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), [точный тег Ollama](https://ollama.com/library/qwen3:4b-instruct-2507-q4_K_M).

Почему этот вариант: есть небольшая фиксированная сборка, можно работать локально после скачивания, не платить за каждый запрос и оставить существующий Java backend. Это кандидат для испытаний, качество русской модерации на ваших материалах пока не измерялось. Веса 2,5 ГБ не означают потребление ровно 2,5 ГБ RAM: нужны память контекста и runtime. Для ноутбука с IDEA, браузером и приложением ориентировался бы на **16 ГБ общей RAM**, контекст модели ограничил бы 8 192 токенами. Это моя инженерная оценка; скорость и память надо замерить. На CPU возможен запуск без GPU, но задержку заранее не обещаю. На минимальный 4-ГБ VPS для приложения эту модель вместе с БД не ставил бы.

Предлагаемый процесс:

1. Сохраняется новая ревизия в обычной очереди. Загрузка и публикация не зависят от скорости модели.
2. Фоновая задача Java берёт id ревизии и её заголовок/текст. Kafka и Python-сервис для этого не нужны: достаточно небольшой очереди задач в PostgreSQL и одного worker.
3. Сначала выполняются правила. Затем backend вызывает только локальный `127.0.0.1:11434/api/chat`, просит JSON по схеме: типы риска, фрагменты, краткое объяснение, предложение «ручная проверка» или «явных проблем не найдено». [API](https://docs.ollama.com/api/chat), [ответ по JSON-схеме](https://docs.ollama.com/capabilities/structured-outputs).
4. Модель не получает пароль, email аккаунта, историю действий и права на инструменты; текст новости передаётся как проверяемые данные. Ссылки она не открывает. Ответ валидируется, выводится как обычный текст без HTML и привязывается к конкретной ревизии. Новая редакция всегда проверяется заново.
5. Создатель/ADMIN видит результат рядом с заявкой и принимает обычное решение. Таймаут, неверный JSON или отключённая модель дают статус «автопроверка недоступна», а не одобрение/отказ. Одна повторная попытка, затем ручная проверка. Решение человека, версия модели/правил и отметка времени сохраняются для разбора ошибок.

Пример подсказки: «В тексте обнаружен номер телефона. Проверьте согласие на публикацию» с выделением фрагмента. Проценты уверенности модели не следует выдавать за измеренную вероятность нарушения. Инструкции внутри новости вроде «игнорируй правила» не должны управлять проверкой; дополнительно нужны тесты на такие входы. Никакие результаты модели не меняют роли, квоты или статус публикации напрямую.

Эта модель проверяет **только текст**. Фото, звук и видеоряд по-прежнему смотрит модератор. OCR, распознавание речи и проверка кадров требуют отдельных моделей, ресурсов и испытаний; их не стоит обещать как часть простой интеграции. Фактчекинг и проверку авторских прав одна текстовая модель также не решает.

Перед включением: 50–100 русских/английских примеров, включая цитаты, университетские объявления, телефоны, спам и корректные спорные новости. Сравнить метки с решениями людей, посчитать ложные срабатывания и время обработки. Первоначально только подсказки, после испытаний можно обсуждать дополнительную автоматизацию отдельно. Пока **Ollama не устанавливалась, модель не скачивалась, интеграции и фоновой очереди нет**.
